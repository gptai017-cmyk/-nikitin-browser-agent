# ЛЕКС → коммерческий контур «Безопасность»: ревизия 05.11.2026

**Статус: DRAFT PR. В production не внедрён. Реальный SOS, ГБР, платёжные и агентские банковские выплаты выключены. Не считать все требования DONE.**

## Наследуемые части

- Существующий MAX Worker и webhook: \`pravo4u-max/worker.js\`.
- Telegram \`@advokat4ubot\`: отдельный существующий production и URL-кнопка «Безопасность», в этой ветке не изменяется.
- Существующий раздел \`/security\`, предварительная заявка \`/security/home\`, существующее страхование \`/store/partners\` без правки, \`/security/emergency\`, \`/security/admin\`.
- Действующие 34 DOCX, Robokassa/бесплатные документы, страховые ссылки и реферальные функции не переписаны.
- Схема \`security_leads\` сохраняется. Аддитивная миграция \`security-intake-ru/migrations/0002_security_commerce.sql\` выполняется после существующей схемы.

## Данные и роли

Миграция создаёт \`security_settings\`, \`security_providers\`, \`security_products\`, \`security_agents\`, \`security_clients\`, \`security_referral_visits\`, \`security_objects\`, \`security_object_users\`, \`security_contracts\`, \`security_payments\`, \`security_ledger\`, \`security_refunds\`, \`security_payout_queue\`, \`security_upsells\`, \`security_events\`, \`security_audit_log\`, представление \`security_agent_totals\`.

- \`security_agents.status\`: PENDING → ACTIVE только после ручной админ-проверки и записи основания в audit.
- \`security_clients.agent_id\`: первый атрибутированный агент после подтверждения телефона. Повторная ссылка для известного подтверждённого телефона не перезаписывает агента; самореферал запрещён. Система хранит доказательство \`verification_method\`, но **SMS/OTP-провайдер пока не подключён**: не использовать публичную заявку как телефонную верификацию.
- \`security_clients.agent_locked_at\`: ставится после первой подтверждённой оплаты. Только администратор может вызвать \`reassign_agent\`, с сохранением old/new, причины и admin.
- \`security_objects\`: для объекта может быть несколько \`security_object_users\`. Активация по одной оплате запрещена — требуется ручное подтверждение провайдера и подписанный договор.
- \`security_products\`: два продукта ПРАЙД в статусе PRELAUNCH, цена в копейках в БД; остальные города — поиск партнёров через существующие заявки, без фиктивного провайдера.
- Агентский кабинет в доменном коде возвращает агрегаты только по \`agent_id\` после \`identity_verified=True\`; публичный доступ к нему пока **закрыт**, поскольку нет настоящей агентской аутентификации, сессий и QR-генерации.
- Админ-интерфейс существующего \`/security/admin\` расширен девятью типами списков, агрегатами и настройками. Доступ через существующий административный ключ — это предварительная защита, **не замена 2FA и RBAC**.

## Платёжная архитектура

\`security-intake-ru/provider_ports.py\` определяет интерфейсы \`PaymentProvider\` и \`SecurityProviderAPI\`. Реальный банк/ПЦН не подключены; адаптеры выбрасывают \`IntegrationDisabled\`. Нет API создания настоящей СБП-ссылки, нет банка, подтверждающего webhook и переводов.

\`confirm_paid()\` — **только внутренняя доменная функция** для уже криптографически проверенного банковского события (реального верификатора webhook пока нет). Не привязывать её к публичному полю \`bank_signature_verified\`. Для тестов используется искусственно доверенное событие без реального движения денег. Оплаченный период определяется по \`contract_id\` и подтверждённым платежам; уникальный \`billing_period\` защищает от двойного начисления за один календарный месяц. Начисление ledger создаётся транзакционно один раз. FAILED не начисляет ничего. \`REFUNDED\`/\`PARTIALLY_REFUNDED\` дают дополнительные отрицательные entries, без удаления истории, с уникальными банковскими номерами возвратов. Chargeback потребует отдельного типа события реального банка, пока не реализован.

\`commission_base\` NET_RECEIVED по умолчанию: \`net_received=amount-payment_fee\`; GROSS_PAYMENT возможен через защищённую настройку. Математика — целые копейки и базисные пункты:
- последовательность 1–12: REACTA 2000 bps, agent 2000 bps, provider 6000 bps;
- 13+: REACTA 2000, agent 500, provider 7500;
- без привязанного агента его доля не становится фиктивной задолженностью, она переходит доле провайдера (следует подтвердить в договоре);
- округление до копейки: остаток у провайдера;
- ledger создаётся на базовую абонентскую плату, а допродажи имеют отдельное поле \`upsell_agent_id\` и комиссию по умолчанию 0;
- \`payout_queue\` только рассчитывает и позволяет одобрить, но никогда сам не отправляет деньги.

Пример для 500 ₽ без комиссии банка: REACTA 100 ₽, агент 100 ₽, ПРАЙД 300 ₽; начиная с 13-го: REACTA 100 ₽, агент 25 ₽, ПРАЙД 375 ₽. При эквайринге 5 ₽ и NET_RECEIVED база 495 ₽: 99 ₽/99 ₽/297 ₽. Это внутренняя модель распределения уже поступивших **ПРАЙД** денежных средств, а не платежи напрямую ЛЕКС.

## Продуктовая навигация и Share

Текущая \`/security\` расширяется: жильё, бизнес, камеры/датчики, существующее страхование, ЧП, стать агентом. \`/security/business\` показывает ориентир 790 ₽/месяц и запрет реального реагирования; \`/security/home\` — 500 ₽/месяц. Админ меняет цены без замены исходников, когда российское хранилище подключено.

В \`section-sharing.js\` добавлены deeplink на конкретные продукты, нативные Share Telegram/MAX и кнопка копирования. Публичный \`ref\` переносится через страницы \`/security/**\` и share-ссылки; только позднее независимое подтверждение телефона превращает атрибуцию в закреплённого агента. Человек может перешарить ссылку, не раскрывая телефон, account ID или личные данные. QR **пока не реализован**.

## Блокеры до production

1. Проверить оператора персональных данных и достаточное правовое основание/согласия для физлиц и кандидатов в агенты, уведомление РКН, хранение/резервирование ПД только в РФ, риски транзита через Cloudflare.
2. Настроить проверенный российский хост и реальный защищённый endpoint, TLS/экран/anti-bot, резервирование, восстановление, удаление по отзыву, смену секретов. Без этого заявочные кнопки продолжают быть заблокированными.
3. Заключить с ПРАЙД договор и утвердить зоны обслуживания, 500/790, кто оператор ПД, лицензия, ответственность, порядок активации объекта и число экипажа.
4. ПРАЙД выбирает банк/эквайера СБП: merchant ID, юридическое лицо-получатель, СБП checkout, идентификаторы платежа/договора, поля и подпись webhook, уникальность событий, комиссии, возвраты/chargeback, callback ретраи; затем полноценные интеграционные sandbox/live проверки.
5. Роль агента: договор маркетинговых услуг/привлечения клиентов, налоговый статус и выплаты. **ФНС исключает агентские/комиссионные договоры из НПД**; статус «самозанятый» в форме не является допуском. Договор именно рекламы/информационных услуг требует отдельной юридической и налоговой оценки по существу, не только по названию.
6. Реальная проверка номера (OTP), объединение дублей между Telegram/MAX/WEB, аутентификация кабинета агента и админа (включая 2FA), QR, расширенная аналитика/CRM, бизнес-заявки в Пензе без фальсификации объекта, фактические платежи и активация охраны. Всё это ещё не сделано.
7. Telegram-проект обновляется своей отдельной безопасной процедурой. Незакрытый PR #377 затрагивает те же файлы MAX/share; перед будущим merge понадобится разрешить конфликт. Не менять production без приёмки.
8. ПЦН/SOS, реальный вызов ГБР и банковские выплаты — отдельный следующий этап. Пользователь запретил запуск автоматически.
