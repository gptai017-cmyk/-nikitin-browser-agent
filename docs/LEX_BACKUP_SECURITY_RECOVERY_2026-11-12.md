1. Проверить GitHub Security / Secret scanning, всю историю Git и Actions на случай утечек ключей и токенов. При находке — сначала отозвать и заменить секрет, затем устранить следы по согласованной процедуре (простое удаление строки не стирает историю).
2. Репозиторий сейчас **public**. Рассмотреть перевод в **private** после проверки того, как это скажется на Actions и текущих интеграциях. Не допускать публикации секретов и персональных данных даже в приватном репозитории.
3. Включить 2FA для GitHub, Cloudflare, Gmail, REG.RU; минимизировать права deploy-токенов, разделить рабочие и резервные аккаунты.
4. **Main branch сейчас без branch protection.** Настроить правила: запрет прямых push и force-push, обязательный PR, успешные проверки перед merge, запрет удаления, ограничение деплоя production.
5. Сначала устранить существующие ошибки GitHub Actions; до этого запрещать автоматическую публикацию любого необследованного изменения.

## P0: настоящий внешний бэкап

1. GitHub: выгрузить **полный Git mirror** с ветками и историей + отдельный ZIP релизного исходного кода; хранить зашифрованно в независимом хранилище, не связанном с тем же GitHub-аккаунтом.
2. Cloudflare: зафиксировать ID активного Worker deployment, конфигурацию, пути и домены, ENV **имена** и список bindings, cron, Webhooks (без значений секретов).
3. Cloudflare Durable Objects: учет `ROBO_ORDERS`, `MAX_CHANNEL_STATE`, `MAX_MIRROR_STATE`, `LEX_GROWTH_TOTALS` из `pravo4u-max/wrangler.jsonc`. Определить реальное хранилище каждого, порядок экспорта и проверенного восстановления. Workers rollback НЕ откатывает данные.
4. Остальные системы: проверить KV `STATE` browser bridge, реальное наличие D1/R2/KV, российские серверы `land-intake-ru` и `security-intake-ru`, данные CRM, заявку в Wrike, параметры MAX/Telegram/Robokassa.
5. Ключи, секреты, webhook verification keys и восстановительные коды хранить **отдельно** в менеджере секретов с доступом только владельцу. Никогда не сохранять в Git, открытый ZIP, письмо, Google Drive по публичной ссылке.
6. Первичные персональные данные граждан РФ — не выгружать в иностранное облако как новый бэкап: проверить требования локализации и выбрать законное защищённое хранение в РФ.
7. Режим: автоматические ежедневные копии данных, снимок кода перед каждым релизом и еженедельный независимый зашифрованный архив. Проверять фактическое восстановление раз в месяц; хранить контрольные суммы.

## P1: защита от атак и перегрузки

- Для коммерческого использования перейти с `workers.dev` на собственный домен, заведенный в Cloudflare как zone; домен можно регистрировать или продлевать в REG.RU, а код и Worker оставить на Cloudflare. **Сначала** проверить ссылки MAX, Telegram, Robokassa, webhook callbacks, сертификаты, DNS TTL и маршруты.
- В Cloudflare включить доступные WAF Managed Rules, bot protection и rate limiting для POST-форм, API, /compose, платежных callback-эндпоинтов с отдельными профилями. Для Robokassa / MAX / Telegram нельзя без тестов ставить CAPTCHA или геоблокировку, иначе блокируются легитимные webhook.
- Для Worker's API — проверка схем запросов и длины полей, ограничение размера запросов, server-side authorization, throttling по endpoint, запрет раскрывать внутренние stack traces, проверка подписей webhook, строгая обработка CORS.
- HTTP Security Headers: nosniff, referrer policy, HSTS на HTTPS, Permissions Policy; CSP и X-Frame-Options применять только после проверки встраивания мини-приложения MAX и платежей.
- Мониторинг: публичные health-checks без раскрытия конфигурации каждые 5–10 минут, аварийное уведомление при повторяющихся 5xx/timeout, наблюдение за GitHub Actions/Cloudflare error rate. Отдельный контроль бизнес-потока: заявки, 34 конструктора, MAX/Telegram, платежи.

## Восстановление при сбое

1. Остановить выкладку и установить причину по Cloudflare / GitHub Logs. Зафиксировать точку восстановления.
2. **Если ошибка только в коде** — Cloudflare > Workers & Pages > `pravo4u-max` > Deployments > меню прежней исправной версии > Rollback; альтернативно `wrangler rollback`. После отката выполнить smoke-test. При миграциях DO откат кода может быть несовместим с новым состоянием данных.
3. Если повреждены данные: восстановить **отдельный** проверенный бэкап конкретного storage. Не подменять данные продакшена тестовой копией.
4. Тест: домашняя страница, /land, /land/penza, карточки, 34 конструктора документов, приём заявки, MAX/Telegram, проверка подписей Robokassa и корректного отображения заказов без реального списания.
5. После восстановления проверить DNS/SSL, доступ по мобильным ссылкам, уведомить владельца, задокументировать инцидент и добавить защиту от повторения.
