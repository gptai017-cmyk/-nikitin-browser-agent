# ЛЕКС — переход на российский домен и российскую площадку

**Дата:** 12 ноября 2026. **Режим:** подготовка, без покупки домена, смены DNS и переключения production.

## Решение

- **Основной кандидат:** `lex4u.ru` (свободность и права на название пока не проверены). Альтернатива `lexpravo.ru`; домен `pravo4u.ru` — только при наличии прав и отдельной необходимости.
- Аудитория: Россия в приоритете, затем русскоязычные за рубежом. Один `.ru`-домен глобально доступен при исправной DNS и сети; зарубежный дубль пока не нужен.
- Доменом должен владеть собственник проекта / его юрлицо, не подрядчик. Для .RU с 1 сентября 2026 регистрация и ежегодная идентификация требуют подтверждения личности через ЕСИА; оформлять в REG.RU только после сверки доступности, права на товарные знаки и владельца.
- Для доступа из РФ **не использовать Cloudflare как единственную точку входа**: по данным Cloudflare, часть российских операторов системно ограничивает трафик к Cloudflare. HTTP 200 из внешнего CI не подтверждает доступность в РФ.
- Выбор для технического пилота: российский VPS, например Selectel VDS 2 vCPU / 4 ГБ / 50 ГБ (публичная базовая цена на дату подготовки 650 ₽/мес, без дополнительных услуг). REG.RU/REG.CLOUD также допустим, если существующий аккаунт уже активен; выбрать по фактическому договору, доступам, резервированию и требованиям защиты персональных данных.
- **Не перенаправлять пользовательский трафик на зарубежный Worker из российского VPS до испытаний на российских сетях**: это не гарантирует обход ограничений и не решает локализацию персональных данных.

## Предпубликационные проверки (обязательны)

1. Проверить домен у аккредитованного регистратора и отсутствие конфликтующих зарегистрированных товарных знаков.
2. Подтвердить регистрацию домена **на владельца**, доступ через 2FA и ЕСИА, закрепить авто-продление и контроль срока.
3. Поднять техническую площадку Selectel/REG.CLOUD в РФ и отдельное staging окружение с минимальными правами. Не подключать боевую БД к staging.
4. Пройти `node scripts/lex-domain-smoke.mjs https://<staging-host>` и регрессию 34 конструкторов.
5. Инвентаризировать **99 ссылок `workers.dev` в исходниках на 12.11.2026**. Не менять без разбора платёжные callback, mini-app endpoints и bot webhooks. Разделить абсолютные ссылки для интеграций и относительные страницы сайта.
6. Проверить из РФ через минимум 3 независимых сети/оператора (мобильная и проводная), из одного зарубежного региона, в MAX WebView и Telegram. Статика, JS, DOCX, формы, платежная тестовая транзакция, HTTP/cert, SEO canonical.
7. Проверить локализацию, правовое основание обработки, публичные документы, ограничения доступа к персональным данным, TLS, rate limits, серверный мониторинг.
8. Только после приёмки установить DNS со сниженным TTL, наблюдать за новыми заявками и платежами; старый адрес сохранять как резерв с явным сценарием rollback.

## Защита

- GitHub: основная ветка сейчас unprotected и репозиторий public. Включить branch ruleset: PR перед merge, обязательный `LEX release security preflight / security` и другие проверенные проверки, запрет force-push / deletion; separate review for deployment workflows; включить secret scanning и 2FA. Перед переводом репозитория в private проверить затронутые Actions и интеграции. GitHub-connector здесь не имеет права изменять rulesets: операция требует отдельного администратора.
- На российском origin: fail2ban / SSH keys, закрытые порты кроме HTTPS, регулярные обновления безопасности, приложение за reverse proxy, ограничения скорости / размера / методов запросов; защита DDoS L3–L4 хостера, при необходимости отдельный WAF L7.
- Для платежей, MAX и Telegram: подписывать и верифицировать webhook, не применять общую CAPTCHA; отдельные лимиты и аутентификация.
- Бэкапы: код отдельно от DB; не сохранять персональные данные в зарубежной резервной копии, если это нарушает требования локализации или договоров; тест восстановления раз в месяц.

## Acceptance / прекращение переноса

**Успех:** сайт из РФ и из-за границы открывается без потери частей страницы; 34 конструктора, MAX/Telegram, Robokassa и заявки работают с сопоставлением в учёте; соблюдены требования 152-ФЗ; есть проверенный rollback на предыдущую инфраструктуру, а резервная БД восстановлена на отдельном тестовом контуре.

**Стоп-факторы:** неизвестный владелец домена; отсутствие проверенного российского origin; непроверенная миграция Durable Objects; конфликт товарных знаков; нет независимого бэкапа данных; на staging один из критичных путей не работает.
